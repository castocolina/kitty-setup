<objective>
Make the config-parse check tell the truth about itself (D-09) and make doctor's three "skipped"
results actual SKIP states (D-13).

Purpose: the parse check is the one gate standing between a mutated `kitty.conf` and the user's next
kitty start, and today it reports a flag that does not exist, discards the only diagnostic that says
what went wrong, and rolls back half of what it changed. Doctor's three false FAILs are grouped into
the same plan because they live in the same file and the same function family — `_check_parse` at
`doctor.py:93-102` (at `02-02`'s `6b26b07`) carries both the wrong label and one of the three false
FAILs, so splitting them would put two plans on one function.

Both are in scope for ASVS V14: the parse check is "validate the config we wrote before trusting it",
and the measured finding that it cannot see a **missing `include`** is a real gap in that control.

commit holding every new case across `test_config_updater.py` and `test_doctor.py`, proven failing from
its own tree; then a `ParseCheckResult` dataclass, a rename-aside payload rollback state machine that
survives Ctrl-C and preserves any stale aside an interrupted install left behind, an

derived from the result, and three real SKIPs.

- **A stale aside is preserved under a dated name, never restored and never deleted. That is the
  choice, and the code justifies it.** An install interrupted between step 1's aside rename and the
  commit or restore (Ctrl-C, a kill, a power loss) leaves `kitty-setup.rollback` behind. Measured
  this session: `Path.rename` of a directory onto a non-empty directory raises `OSError: [Errno 39]
  Directory not empty`, so without handling, **every** later install fails at step 1 with no
  explanation. Deleting the aside by hand is the obvious workaround, and it can destroy the only good
  copy of the previous payload. Two behaviours were considered: restore the aside when the payload dir
  is missing, or preserve it under a unique dated name. The second is chosen, for three reasons, all
  from the code:
  1. `install()` always replaces the payload with `payload_source` (docstring `:224-225`, "mirrored
     into `paths.payload_dir` (overwriting)"). A restored aside would be moved aside again by the very
     next step and dropped on success, so restoring buys nothing that preserving does not.
  2. `install()` keeps no journal of which step was interrupted. The commit step's `shutil.rmtree` of
     the aside unlinks entry by entry, so an interrupted **commit** leaves a partial aside that looks
     like a whole one. Any rule that puts an aside back into live use has to guess; preserving never
     guesses.
  3. It is one code path and one test, with no branch on whether the payload dir exists.
  The dated name is `paths.kitty_dir / f"{aside.name}.{_utc_timestamp(now)}"`, for example
  `~/.config/kitty/kitty-setup.rollback.20260924T120000Z`. That is the directory where `_backup`
  writes `kitty.conf.bak.<ts>` (`:157-161`), the same filesystem, so the rename is atomic. It reuses
  `BACKUP_SUFFIX_FMT` (`:55`) so it dates like the backups beside it. It is **unique**: when the name
  is taken (two interrupted installs in one second), append `.1`, `.2`, … choosing the smallest free
  suffix, and never rename onto an existing path. Measured: renaming onto an *empty* directory succeeds
  and silently replaces it, so "taken" means "exists", not "is non-empty". Two consequences are
  stated, not fixed. `BACKUP_NAME_RE` (`:58`) does not match the dated name, so `list_backups` and
  `prune` never touch it. And `uninstall()` removes only `paths.payload_dir` (`:325-327`), so the
  preserved copy also survives `my-kitty uninstall`. It is the user's to delete, which is exactly why
  the report line names it. The report is **one line on stderr**, printed at the moment of the move,
  of the form `config: preserved a payload aside from an interrupted install at <path>`. It is printed
  rather than carried on `InstallResult`, because the result object is never returned when the install
  that follows fails, and that is when the path matters most. `cli_install` already reports
  `install failed: …` on stderr (`installer.py:438` at `6b26b07`), so both lines land on the same
  stream, in order. If the preserving rename itself fails, raise `ConfigUpdaterError` naming the stale
  aside and the intended destination, before anything else has been touched.
- **The rollback handler catches `BaseException`, not `Exception`.** `KeyboardInterrupt` and
  `SystemExit` derive from `BaseException` directly (measured:
  `issubclass(KeyboardInterrupt, Exception)` is `False`). An `except Exception` handler would let a
  Ctrl-C mid-copy skip the restore and leave exactly the stale aside the previous bullet has to
  handle. The handler never swallows: it restores, then re-raises the original with a bare `raise`.
  Measured on a scratch prototype: `except BaseException as exc:` with a bare `raise` passes
  `ruff check` and strict `pyright` with no suppression comment.
- **Restore failures name the aside, and the ordering is fixed.** The conf restore stays exactly where
  it is today: inside the checked region, on the parser's rejection only, **before** the rejection is
  raised. So by the time the payload rollback runs, a rejected conf is already back. A copy failure
  happens before the conf is touched, and a mutation failure leaves the conf as today's code does;
  neither behaviour changes. The payload rollback removes the partial target, then renames the aside
  back. If **either** of those raises `OSError` while an aside exists, the aside is kept and
  `ConfigUpdaterError` is raised `from` that `OSError`. Its message names the aside path and the
  payload path, and repeats the original failure's message, so a rejection's command and stderr are
  not lost behind the restore error. The original stays reachable as the `OSError`'s `__context__`.
  With no aside (a failed first install), nothing of the user's is at risk: a removal `OSError`
  propagates as is, chained to the original, and names the path itself. The commit step's `rmtree` of
  the aside runs **after** the checked region, so its failure can never roll back an accepted payload.
  A leftover aside from that failure is exactly the stale-aside case the next install preserves and
  reports.
